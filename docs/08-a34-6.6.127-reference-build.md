# 08 — Build de referencia A34 6.6.127

## Qué se audita

El tag `6.6.127_2026-04-06_A346BXXSEEZB6` de `UN1CA/kernel_samsung_a34x`:

- `kernel-6.6` apunta a `UN1CA/kernel_samsung_mediatek_common`
  `2415ac269f13919d8c855f495cb141268e8751bb`, `SUBLEVEL = 127`.
- `kernel/kernel-6.6` es un symlink a `../kernel-6.6`.
- `kernel/kernel_device_modules-6.6` contiene el BSP MT6877 y los overlays.
- `build_kernel.sh` es el procedimiento oficial y también lo usa el workflow
  `.github/workflows/build_kernel.yml` del propio repositorio.

## Procedimiento oficial (sin cambios)

```sh
repo init -u https://android.googlesource.com/kernel/manifest \
          -b common-android15-6.6 --depth=1
repo sync -j$(nproc)
# Clang r536225 en prebuilts/clang/host/linux-x86
ln -s <aosp>/prebuilts kernel/prebuilts
cd kernel
python kernel_device_modules-6.6/scripts/gen_build_config.py \
  --kernel-defconfig mediatek-bazel_defconfig \
  --kernel-defconfig-overlays "sec_ogki_fragment.config mt6877_overlay.config mt6877_teegris_5_overlay.config" \
  -m user -o ../out/target/product/a34x/obj/KERNEL_OBJ/build.config
DEVICE_MODULES_DIR=kernel_device_modules-6.6 \
BUILD_CONFIG=... PROJECT=mgk_64_k66 MODE=user \
  ./kernel_device_modules-6.6/build.sh
```

El laboratorio no reescribe ese script: lo ejecuta tal cual y conserva el log.

## Si falla

- **Disco**: el log dirá `No space left on device`. El workflow libera espacio
  antes del build; si no basta, hace falta un runner mayor.
- **RAM/OOM**: Kleaf/Bazel puede necesitar más de 16 GB. No se oculta: se
  conserva el log y se separa fallo de infraestructura de fallo de código.
- **Target**: si `mgk_64_k66_kernel_aarch64.user` no existe, el log de Bazel
  lista los targets reales. No se inventa una ruta.

### Dato importante para el Hito 2

El `Image` de referencia es el **núcleo GKI** (38 MB, config con
`CONFIG_NAMESPACES=y` pero sin `CONFIG_PID_NS`, `CONFIG_SYSVIPC` ni
`CONFIG_MTK_PLATFORM`). Los drivers MTK del A34 se compilan aparte como
módulos (`mgk_64_k66.user/.../*.ko`) y el build también produce
`boot.img`, `boot-lz4.img`, `boot-gz.img` y `boot-img.tar.gz`.

Es decir: el A34 no es un BSP monolítico como ruby; es GKI + módulos. Eso
condiciona el Hito 2: hay que decidir si ruby se porta como GKI + módulos
(como el A34) o con los drivers MTK built-in (como el kernel stock actual).

`find -print -quit`, hashes relativos al directorio de artefactos y extracción
del DTB desde `boot.img`.

El único fallo fue `DTB_VERIFIED`: el target GKI
`mgk_64_k66_kernel_aarch64` produce `Image`, `Image.gz`, `System.map`,
`vmlinux`, `Module.symvers` y `boot.img` (header v4, sin ramdisk ni DTB), pero
**no compila DTB/DTBO**. Los DTS del A34 viven en
`kernel/kernel_device_modules-6.6/arch/arm64/boot/dts/mediatek/a34x/` y los
genera el build de Android, no este target de kernel.

Por eso la verificación ahora marca `DTB/DTBO` como `N/A` con justificación, en
vez de fallar. No se inventa un DTB que el target no produce.
